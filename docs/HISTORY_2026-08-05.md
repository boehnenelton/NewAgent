## v2.21.0 pkg046 — 2026-07-27T04:00:00Z

Added the 3-row header + 1-row footer Elton described. Assumption stated explicitly since the two button actions weren't named: mapped them to Settings (opens the existing overlay, same as typing /settings) and Clear (wipes the log, same as typing clear) -- the two lowest-risk, already-existing actions, rather than inventing new behavior. Row 1 (buttons): background transparent (matches #terminal's own background exactly -- 'same background color so it looks seamless'), border transparent by default, red bold text signaling they're interactive; border becomes visible (red) only on hover/focus as a subtle affordance. Rows 2-3 (status): MODEL / ENGINE / KEYS on row 2, TURNS / EXECS / STATUS on row 3, red labels + white values matching the existing .prompt convention already used for the command-line prompt -- no new color introduced, stayed inside the white/black/red palette (deliberately did not use a green status dot, which would have been the obvious choice outside that constraint). Footer: single row below the input line showing CWD, red label + white path. Fixed a real scroll-containment bug this required: #terminal previously had overflow-y:auto on the WHOLE container, meaning a new header/footer would have scrolled away with the log content the moment there was enough output to scroll -- defeating the point of a persistent header/footer. Changed #terminal to overflow:hidden and gave #log-container its own flex:1/min-height:0/overflow-y:auto, so header and footer (flex-shrink:0) now stay pinned while only the log area scrolls. Extended GET /api/status with the fields the header actually needs: engine, turns, execs, keys_available (computed via the existing KeyRegistry._is_available() check, same method /keys already uses -- not a new availability calculation). Frontend polls /api/status every 4 seconds and updates all three status rows plus the footer CWD in one pass; falls back to a plain 'OFFLINE' status word (no color trick) if the poll fails. CWD footer also updates immediately after every command (chat-driven or raw !exec) rather than waiting for the next poll cycle, via a shared updateCwdDisplay() call added at both existing cwd-update sites. Found and fixed a real undercounting bug during testing: self.stats.execs only incremented for chat-driven actions (via run_action_queue), not for the raw '!command' escape hatch (which calls do_exec directly, bypassing that counter) -- the header would have shown an inaccurate EXECS count depending on which path was used. Added the increment to /api/exec directly; confirmed by test that the count is now correct and shared correctly across both paths. Verified: served page contains all new header/footer markup and element IDs; /api/status returns all four new fields with correct initial values; execs count increments after a raw exec; execs AND turns both increment correctly after a chat-driven action (2 prompt() calls from the auto-continue loop = turns:2, one <exec> tag = execs:2 total, shared with the prior raw exec); full regression re-run of config/files/quickjumps/chat/attachments confirming no regression elsewhere. JS re-checked with node --check before embedding, same discipline as every prior webagent.py change. Version bump: webagent.py 0.4.0 -> 0.5.0.

## v2.24.0 pkg049 — 2026-07-27T05:30:00Z

Fixed the recurring key-exhaustion crash Elton has raised multiple times: repeatedly-failing keys were never actually pruned from rotation, only temporarily cooled down -- meaning a run of exhausted/rate-limited keys could exhaust all retries repeatedly, tripping the app-level circuit breaker (3 consecutive TURN failures -> clean shutdown), which from the outside is indistinguishable from a crash. Confirmed by reading the code that no automatic per-key deactivation existed at all -- deactivate_key() (built in pkg037) was only ever reachable via the manual /keys deactivate command, and clear_cooldown() was defined but never called anywhere, meaning cooldowns only ever expired by time passing, never cleared early on a real success. Added real per-key consecutive-failure tracking to KeyRegistry: new AUTO_DEACTIVATE_THRESHOLD=3 constant; set_cooldown() now increments a per-key fail count on every 429/401/403/HTTP-error, and once a key hits 3 consecutive failures it is automatically deactivated (is_active=False, removed from rotation) via the existing deactivate_key() path -- the exact 'pluck them out on repeated fails' behavior requested. New mark_success() resets a key's fail count to 0 and clears its cooldown early the moment it actually succeeds -- wired into prompt()'s real success path, where no success-tracking call existed before at all. Extended _STATE_FIELDS with a fail_count column so this survives a restart, not just one session -- backward-compatible load (older state files without the column default to 0). Also fixed the persistence logic itself while building this: the original _save_state only ever wrote rows for keys currently in _cooldowns, meaning a fail count reset to 0 by mark_success (once a key's cooldown clears) would never actually get written to disk -- a restart could reload a stale pre-recovery count. Changed to persist the union of cooldowns and fail_counts. Verified thoroughly, not just spot-checked: 2 consecutive failures leave a key in rotation, the 3rd correctly deactivates it with is_active=False persisted to disk; a success via mark_success resets the count so a subsequent failure streak needs the full 3 again, not a carried-over 1; fail count and the correct post-reset behavior both survive a simulated restart (fresh KeyRegistry load from the same files); and critically, an end-to-end test through RestPrompter.prompt()'s REAL HTTPError(429) handling (not a direct unit call to set_cooldown) confirms the actual retry loop wiring wires all the way through to auto-deactivation. Confirmed the existing manual /keys deactivate command still works unchanged alongside this. Full compile sweep across every touched file. Version bump: lib_bejson_newagent_engine_rest.py 1.11.0 -> 1.12.0.
